# ADR-0001: Automated PR Review as a Fabric App

**Status:** Accepted
**Date:** 2026-03-14
**Author:** ry-ops

---

## Context

The git-fabric ecosystem has security scanning at the infrastructure layer (`eagle-scout` for container CVEs, `@git-fabric/cve` for dependency advisories, `@git-fabric/sandfly` for runtime threat detection) but no coverage at the development layer — the pull request.

PRs are where security issues, dependency risks, and Dockerfile misconfigurations are introduced. Today, these are caught manually (if at all) or only after merge when a downstream scanner flags the issue. The gap between "code written" and "vulnerability detected" is the most expensive place to find bugs.

The team recently performed manual PR-level security analysis on external projects (TerraInk, Overstory) and identified a repeatable pattern: clone, analyze diffs, check for secrets/injection/CVEs, post findings. This pattern should be automated and made available as a fabric app.

### Options Considered

1. **Fork Overstory** — Multi-agent orchestrator with reviewer agent pattern. Rejected: tmux-based local execution conflicts with the remote-first fabric model. Heavy runtime dependency (SQLite messaging, git worktrees) for what is fundamentally a diff analysis problem.

2. **GitHub Actions marketplace action** — Run a third-party review bot. Rejected: does not integrate with the fabric gateway, no MCP tool access, no cross-referencing with existing fabric apps (cve, eagle-scout).

3. **New fabric app (`@git-fabric/review`)** — Build a purpose-built review engine following the same `FabricApp`/`FabricTool` contract as existing apps. Integrates natively with `fabric-ctrl` gateway, can call sibling apps (cve, git), and plugs into existing automation pipelines.

## Decision

Build `@git-fabric/review` as a standard fabric app that:

1. **Exposes MCP tools** (`review_pr`, `review_diff`, `review_scan_repos`) via the `fabric-ctrl` gateway
2. **Runs pluggable analyzers** — each analyzer is an independent module that receives the PR diff and returns typed findings
3. **Ships with three built-in analyzers**: security (secrets, injection, XSS), dependency (manifest changes, lockfile integrity), and dockerfile (unpinned images, build secrets)
4. **Posts structured review comments** to GitHub PRs with severity-annotated findings and actionable suggestions
5. **Follows the same conventions** as `@git-fabric/cve`: TypeScript, ESM, `createApp()` factory, plain JSON Schema input schemas, non-fatal execution

### Architecture

```
fabric-ctrl (gateway)
    |
    +-- loads @git-fabric/review via gateway.yaml
    |
    +-- review_pr tool called (MCP or invoke)
           |
           +-- fetches PR metadata + diff from GitHub API
           +-- runs analyzers in sequence
           +-- aggregates findings
           +-- determines verdict (approve / comment / request_changes)
           +-- optionally posts review to PR
```

Analyzers are pure functions: `(pr, files) => findings[]`. No shared state, no side effects. New analyzers (CVE, quality, AI-assisted) can be added without modifying the core review loop.

### Future Integration Points

- **eagle-scout**: When a Dockerfile change is detected, trigger `scout_cves` against the new base image and include CVE delta in findings
- **@git-fabric/cve**: Cross-reference PR dependencies against the CVE queue
- **Aiana**: Include review summaries in daily ops briefings
- **GitHub Actions**: Trigger `review_pr` automatically on PR open/synchronize events

## Consequences

**Positive:**
- PR-level security coverage closes the gap between code authoring and vulnerability detection
- Pluggable analyzer architecture allows incremental capability additions
- Native fabric integration — accessible from Claude Code, Aiana, invoke sequences, and GitHub Actions
- Same `FabricApp` contract as all other apps — no new patterns to learn
- Findings are structured and machine-readable, enabling downstream automation

**Negative:**
- Pattern-based detection has inherent false positive/negative rates — not a substitute for human review on critical paths
- GitHub API rate limits apply — scanning many repos with many open PRs requires throttling
- No AI-assisted analysis in v0.1.0 — initial analyzers are regex-based; semantic understanding requires future work
